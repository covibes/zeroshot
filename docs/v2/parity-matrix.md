## 2. Binding process rule

> **Every Node feature PR merged after `50c5b00` must append a row to the Delta Log (§9) before it is eligible to merge.**
>
> **A Node PR that changes user-observable behaviour and lands with no Delta Log row is a parity defect**, attributable to that PR, and is fixed by amending this document — not by amending the Rust issue that later discovers the drift.

Scope of "user-observable": anything an argv-driven invocation of the binary can reveal — stdout, stderr, exit code, files written, network calls made, prompt text emitted to a provider CLI, settings keys read or written, message topics published. Internal refactors with no observable delta need no row.

Enforcement (ENFORCE > DOCUMENT): this rule is only real once it is a merge gate. Required before freeze — a CI check on the Node repo that fails a PR touching `cli/`, `src/`, or `lib/` unless the diff also touches this document's Delta Log, waivable by an explicit `parity: none` label. Until that check exists, this rule is honour-system and the matrix should be assumed stale.

Watch paths with the highest observed churn rate: `src/agent-cli-provider/adapters/*.ts` (model catalogues, auth modes, feature probing) — two capabilities in §7 were introduced by `50c5b00` itself and by #807 immediately before it, and both landed unowned.

## 3. How to read this document

### 3.1 The four classifications

Every row carries exactly one classification. Classification determines the test obligation; it is not a value judgement.

| Class              | Meaning                                                                      | Test obligation                                                                                                                                                                                                                     |
| ------------------ | ---------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **implemented**    | V2 must reproduce the Node observable. Same inputs → same observable output. | A dual-binary behaviour-spec case. Node is the oracle; the spec asserts both binaries produce the same normalized observable. Divergence is a V2 bug.                                                                               |
| **replaced**       | The observable is preserved but the mechanism is unrecognisable.             | Test the **preserved observables only** against both binaries. Mechanism assertions are written against the _Rust_ specification (e.g. the #758 receipt algebra), never against Node internals. Do not port Node's mechanism tests. |
| **excluded**       | The capability will not exist in V2.                                         | No behaviour test. Requires (a) a link to the recorded decision and (b) a negative assertion: the surface is absent and the binary fails with a documented, actionable error rather than silently mis-executing.                    |
| **absent-in-node** | #665 requires it; Node never implemented it.                                 | Nothing can be ported. Specified from scratch against the owning issue's acceptance criteria; Rust-only conformance test. See §8.                                                                                                   |

Two orthogonal flags sit alongside the classification:

- **`unowned`** — no #665 sub-issue claims the capability. Orthogonal to class: a row can be `parity` _and_ `unowned`, which means "V2 must reproduce this and nobody is building it". §7 is the full set.
- **`cliObservable`** — see §3.2.

### 3.2 What `cliObservable` means

`cliObservable: true` means the row is assertable by driving the binary as a subprocess: argv in; stdout / stderr / exit code / filesystem effects / spawned-process argv out. **The dual-binary behaviour-spec suite is exactly the set of `cliObservable: true` rows.** One spec file, two binaries, normalized comparison (cluster ids, timestamps, elapsed times, absolute paths, and PIDs are normalized; everything else is compared literally unless the row says otherwise).

On the engine surface, 79 of 98 rows are `cliObservable`.

`cliObservable: false` was assigned for four reasons, and each carries a different substitute obligation:

| Reason                                                                     | Examples                                                                                                                                                                          | Substitute evidence                                                  |
| -------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| Prompt-injection knobs (no argv-visible effect other than model behaviour) | `--workers` fan-out cap, per-complexity `max_tokens`                                                                                                                              | Assert the constructed prompt/context bytes in-crate.                |
| TTY-only rendering                                                         | live status footer, terminal title, attach key bindings                                                                                                                           | Golden-frame test against a PTY harness, or an accepted #691 waiver. |
| Interactive wizards                                                        | first-run setup, `providers setup`                                                                                                                                                | Scripted-stdin transcript test, or waiver.                           |
| In-process mechanisms with no argv path                                    | guidance API, sub-clusters, snapshotter, stuck detector, keychain preflight, error classification, redaction, consensus semantics, observation sink, adversarial-tester role text | In-crate unit/property tests named explicitly in the row.            |

A `cliObservable: false` row with no named substitute evidence is an audit failure at #691, not a pass.

### 3.3 excluded-by-decision vs excluded-by-consequence — read this

`excluded` rows split into two kinds. The distinction is the single most important thing in this document.

**excluded by decision** — #665 (or a named sub-issue) explicitly names the capability and states it is out of scope. The loss is intentional, attributable, and reviewable. Example: the guidance mailbox, excluded at #665 line 414.

**excluded by consequence** — nobody decided anything. The capability fell out of a constraint written for another purpose, and **no owner recorded the loss.** There is no issue to argue with, no line to cite, and no migration note. The first person to notice is a user.

Known excluded-by-consequence cases already identified:

### 3.4 Two contradictions that must be resolved before rows can be certified

- `--close-issue` takes `auto|always|never` in Node (`src/agents/git-pusher-template.js:308`). #680 defines dispositions `never|success|failure|indeterminate`. **No mapping is stated.**
- #677's acceptance criterion "Docker never mounts home / socket / broad host paths by default" directly contradicts Node defaults: `dockerMounts` defaults to `['gh','git','ssh']` (three home-dir mounts, `lib/settings.js:105`) and `_buildBaseDockerArgs` unconditionally mounts `/var/run/docker.sock` and adds the docker group (`src/isolation-manager.js:339-353`). Intentional security fix; silently breaks every workflow where the containerized agent runs `git`/`gh`/`docker`.

Two Node behaviours are recorded as **do-not-reproduce**, not parity:

- The foreground banner is factually wrong today: `printForegroundStartInfo` (`cli/index.js:397`) says "Ctrl+C to stop following (cluster keeps running)", but `setupForegroundSigintHandler` (`cli/index.js:585`) calls `orchestrator.stop()`. #687 must pick one documented behaviour rather than inherit the contradiction.
- `run` exits 0 in the foreground even when the cluster reaches a failed terminal state (`cli/index.js:608` waits only for `state !== 'running'`). #767 owns deterministic exit status.

Also note: CLAUDE.md's CLI Quick Reference is stale in two places — `zeroshot clear` does not exist (renamed to `purge`; only a residual `'No clusters or tasks to clear.'` string remains at `cli/index.js:3711`), and `settings` with no subcommand prints the list plus usage (`cli/index.js:4341`). The rows reflect the binary, not the doc.

## 4. Why the Node test suite is not the V2 regression net

| Measurement                                                | Value                           |
| ---------------------------------------------------------- | ------------------------------- |
| Node test files                                            | 214                             |
| Files that `require()` a `src`/`lib`/`cli` module directly | **159** (74%)                   |
| Files that drive the real binary                           | **10** (`tests/e2e`)            |
| Test cases in `tests/e2e`                                  | **~23**                         |
| Files that drive `zeroshot run -d` as a subprocess         | 1 (`cluster-lifecycle.test.js`) |
| Matrix rows                                                | 281                             |

159 of 214 test files import implementation modules directly. They assert internal function contracts, not user-observable behaviour, and are therefore **untransferable by construction**: a Rust binary has no `src/lib/cli` module to require. Porting them is not possible and attempting it would encode Node's internal decomposition into V2's design.

`tests/e2e` — the only subprocess-driven set — covers cluster lifecycle, worker, worker-validator, single-worker, resume/detach daemon, stuck-agent recovery, worktree no-leak, and copilot. It **does not touch delivery, Docker, issue providers, or the gateway at all.** ~23 cases against 281 rows means the overwhelming majority of `cliObservable` rows are unasserted in Node today.

**Consequence for #691:** the parity audit cannot lean on the Node suite. It must build the dual-binary behaviour-spec harness itself, and that harness is the deliverable that makes this matrix checkable. Budget it as new work, not as porting.

**Consequence for delivery specifically:** there is no deterministic Node behaviour to conform to. `src/agents/git-pusher-template.js` is 33 KB of which ~24 KB is English prompt text; the GitHub `createCmd` at `:415` is a template string inside a markdown-fenced "MANDATORY STEPS" block (`:518-555`) that an LLM is _asked_ to execute, with all-caps admonitions that exist precisely because models skip the step. `src/agent/pr-verification.js` (22 KB) then re-derives what actually happened by parsing claimed `pr_url`/`pr_number` out of free text (`:229 extractPrInfoFromRawOutput`) and cross-checking with `gh pr view --json`. **Do not write conformance tests "against Node behaviour" for delivery** (#758/#759/#760/#680/#682/#762). Write them against the #758 receipt algebra, and treat the Node prompt only as an inventory of which forge operations must exist: branch, commit, push, pr-create, checks, auto-merge, merge-queue, merge, issue-close.
